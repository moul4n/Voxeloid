Vox Speed Bible

Starting point

What we know, and what we're deliberately leaving blank

The game has no name, no story and no core mechanic yet. That's intentional. The genre we're aiming at (short runs, fast pace, buffs that multiply into chaos; think The Gnorp Apologue and the small asteroid-mining idle games in the same space) lives or dies on how it feels at high density, and feel is impossible to judge in a design doc. So this document commits to the technical and visual foundation, states the pillars that every later mechanic must serve, and lists the decisions we're parking until the stress bed proves the foundation.

Rule for this phase: nothing goes in the project that doesn't help answer "can we keep 200 fps with several thousand animated vox sprites on integrated graphics?" No menus, no progression, no save system, no story.

Pillars

Four things every later decision is checked against

Speed

Runs are minutes, not hours. Input to on-screen reaction is one frame. Nothing waits on a tween to finish before you can act again.

Compounding

Buffs never touch numbers directly. They add tags and modifiers, and mechanics interact through tags, so combos emerge without bespoke code per pairing.

Density

The screen should get fuller as a run progresses. Spam is the reward. The renderer must handle the ridiculous late-run state, not the polite early one.

Different every time

Progression is generated from a seed with weighted, tag-aware offers. Two runs should look like two different games by the halfway point.

Phase 0

The stress bed

A single Godot scene with a debug overlay and keyboard controls. No gameplay. Its only job is to produce numbers we trust and a visual we like.

What it contains

  • One baked vox "guy" rigged as separate parts (head, body, two legs, one tool) that idles, walks and swings using tweens only.
  • A spawner that throws N vox debris sprites (rock chunks, sparks, shards) with velocity, gravity, bounce and fade. N is bound to keys: 100, 1k, 5k, 20k.
  • A "buff stack" toggle that layers visual effects on everything on screen: tint, emission glow, scale pulse, trail, extra particle emitter. Each key adds one more layer so we can watch the cost climb.
  • A debug overlay: fps, frame time (ms), physics time, draw calls, live node count, live instance count, GPU name.
  • A capture mode that records 10 seconds of frame times to a CSV so results are comparable across machines.

Budget

Frame budget

Everything below is per frame and has to fit in the budget of the fps we're targeting. Physics runs on its own fixed tick so it doesn't scale with render rate.

Target fpsFrame budgetWhat has to fit

2404.17 msWhat a 240 Hz monitor owner should see most of the time.

Physics tick60 Hz fixedInterpolation on, so movement stays smooth at any render rate.

At the dev-PC target of 300 fps the whole frame is 3.33 ms: render ≤ 1.8 ms, script (spawner, tweens, event bus) ≤ 1 ms, physics amortised ≤ 0.3 ms, headroom ≈ 0.2 ms. The overlay reports each so we can see which bucket is blowing up.

Rendering

Density tiers: not everything is a node

In 2D Godot the frame rate killers are node count and draw calls, not pixel fill. So on-screen things are split into three tiers by how much individuality they need, and the tier decides how they're drawn.

TierWhatHow it's drawnBudget
HeroPlayer, bosses, anything with a part rig and per-object tween animationNode2D with child Sprite2D parts, tweens, per-node shader≤ 50 nodes
ActorEnemies, pickups, projectiles that need collision and individual statePooled scenes (never instantiate() mid-run), Area2D overlap, one Sprite2D each≤ 1,500 nodes
SwarmDebris, shards, sparks, chunks, number popups; anything that only needs position, rotation, scale, colour, frameOne MultiMeshInstance2D per atlas, transforms + custom data updated from a packed array each frame; motion computed in a tight loop, or moved to the vertex shader≤ 20,000 instances, 1–3 draw calls

The swarm tier is the phase 0 risk. GDScript iterating 20k instances per frame will not fit 4 ms. Plan A is to keep per-instance motion in the MultiMesh's custom data and integrate it in the vertex shader (position += velocity × t, gravity, fade by age), so the CPU only writes on spawn. Plan B is a C# or GDExtension update loop. Phase 0 measures both.

Particles (GPUParticles2D) are a fourth path for pure eye-candy with no gameplay meaning: trails, glow motes, dust. Compatibility renderer supports GPU particles; CPUParticles2D is the fallback if a specific iGPU driver misbehaves.

Art

Vox in, sprites out

We keep the voxel workflow because it's fast to author and chunky to look at, but nothing is voxel at runtime. Every model is baked to a sprite sheet once.

Pipeline

  • Model in MagicaVoxel on a 16³ or 32³ grid. One .vox per part, not per character, so parts can be swapped and recoloured independently.
  • Bake with a headless Blender script (import vox → orthographic camera → render 8 yaw angles for things that turn, 1 for things that don't) at 2× target size, then downsample with nearest-neighbour to keep the voxel edges crisp. Output one atlas per model and a JSON of frame rects.
  • Import into Godot with filter off, mipmaps off, atlas packed by the importer. Palette is a shared 32-colour ramp so tinting and emission shaders behave the same on every sprite.
  • Rig hero-tier things as a parts tree: Guy/Body, Guy/Head, Guy/LegL, Guy/LegR, Guy/Tool. Pivot points set at joints. Animation is code-driven tweens on rotation, scale and offset; there are no hand-keyed frames.

Because animation is procedural on rigid parts, a new character costs one afternoon of vox modelling and zero animation work. That's the property the whole game leans on.

Art direction

What a vox is, and where the pretty comes from

A .vox is a 3D grid where each cell is empty or holds one byte: an index into a 256-colour palette. A 16³ model is 4,096 cells and a character is usually under a thousand filled ones. No textures, no UVs, no normals. The colour lives in the palette, not the model, and almost everything below is a consequence of that.

Three sources of the look

Palette

Voxel art is palette art. One shared ramp of 24–32 colours, each hue in 4–5 shades. Everything built on it belongs together automatically, and tint and hue-shift shaders behave predictably because they act on known ramps.

Baked lighting

The bake gives real directional light, ambient occlusion in crevices, soft shadow and a rim light for free. One fixed light (top-left, slightly front) for every bake so the whole game reads as one lit world despite being flat sprites.

Materials

MagicaVoxel palette slots can be emissive, metal, glass or rough. A fire shard is a rock shard with one slot swapped to emissive orange, not a new model. This is the main lever for buff visuals.

Palette spec

Slot rangePurposeNotes
1–5Neutral rampNear-black to off-white; shared shadow and highlight steps for every model
6–29Six hues × 4 shadesRock grey-brown, ice blue, ember orange, acid green, crystal violet, gold. Each hue's shades are evenly spaced in lightness so the tint shader can shift the whole ramp
30–32EmissiveEmber, arc-blue, toxic green. Flagged emissive in MagicaVoxel so the bake blooms them
200–215ID paletteSixteen flat "role" colours (base, shade, highlight, accent, emissive…) used for the neutral bake that the runtime remap reads. Never seen on screen

Rule per model: at most two hues from the ramp plus the neutral shades. Saturation lives in the buff layers, not the model. Busy models plus busy effects at 10,000 instances is mud; quiet models plus loud effects is the look we want.

How variety is manufactured

  • Palette swap. The model stores indices, so the same vox under a different palette is a different object at zero authoring cost. Preferred form: bake once in the ID palette, then remap in the shader at runtime from a 16-entry lookup. One rock atlas becomes ice, lava, crystal and gold rocks, and a buff can retint a whole category live.
  • Part swap. A guy is head + body + legs + tool; five of each gives 625 combinations. Rocks are core shape + crust layer + inclusion. Parts share pivots so any combination rigs without adjustment.
  • Procedural voxels. A grid is trivial to generate in code. Rocks are spheres carved by 3D noise, debris is a random 3–5 voxel blob, crystals are extruded hexagons. Phase 0 gets a small Python generator so the debris set has a hundred distinct chunk shapes without opening MagicaVoxel.
  • Rotation for free. One bake yields 8 yaw angles from the same model; hand-drawn sprites would need each drawn.

Grid sizes and on-screen scale

At 960×540 with a 2× window, a 16-voxel guy is about 24 base pixels tall, which is the right size for "tiny things, thousands of them". Bake at 2× and nearest-downsample so cube edges stay crisp. Keep an unlit flat pass alongside the lit one: tint and glow shaders multiply against the flat pass so buffs don't fight the baked shadows.

Animation

Compounding animation is a layer stack, not a set of clips

The pitch says "animations compound". Concretely: every buff may declare a visual layer, and layers are additive effects attached to whatever the buff touches. Ten buffs on a rock means ten layers on the rock, none of which were authored for that combination.

LayerMechanismCostStacks how
TintShader uniform, modulateFreeMultiplies; capped at 3 tints, later ones blend at 50%
Emission / glowShader: additive pass on palette-masked pixelsCheapIntensity sums, colour blends
Scale pulseTween on scale, phase from instance seedCheapAmplitudes sum, frequencies stay distinct so it looks alive not noisy
Wobble / squashVertex shader driven by TIME + seedFree on GPUSums; hero tier only
TrailLine2D or ghost sprites from poolMediumOne trail per object, colour from strongest tint
EmitterChild GPUParticles2D, shared material per buffMedium–highCapped at 2 per object; extra buffs raise emission rate instead
ScreenGlobal: shake, chromatic pulse, hit-stopFreeNever stacks; strongest event wins, cooldown 80 ms

Every layer takes its phase from a per-instance seed and its magnitude from the stat resolver, so the same buff looks slightly different on every object and scales visually as the build scales numerically. Caps exist so density never turns into mud.

Architecture

Core systems (built after phase 0, designed now)

These are the four pieces that let mechanics combine without per-pair code. They're listed here so phase 0 doesn't paint us into a corner, but none of them are written until the renderer passes.

1. Stat resolver

Every gameplay number is a Stat: base value plus a list of modifiers, each carrying a tag set and a layer. Resolution is cached and only recomputed when a modifier is added or removed.

value = (base + Σ add) × (1 + Σ increased) × Π (1 + more)
        filtered to modifiers whose tags ⊆ the entity's tags

2. Event bus

One autoload emits typed events: hit, kill, crit, split, pickup, tick. Buffs subscribe with on / if / do triples and their effects may emit further events. Each event carries a depth counter capped at 8 and the bus enforces a per-frame spawn budget. Chain reactions are allowed; fork bombs are not.

3. Tags on everything

A projectile is not a FireProjectile class. It's a pooled scene with tags = [projectile, fire]. Modifiers and buff conditions match on tags, so "fire things pierce" applies to anything that acquired fire, however it got there.

4. Visual layer binding

The same handler that applies a buff's mechanical effect attaches its visual layer to the same tagged entity. There is no separate "animation for buff X on object Y" step, which is the whole reason the art stays cheap.

Buff as data

# res://buffs/shatter.tres  (Resource, generated or hand-written)
name        = "Shatter"
tags_add    = ["shard"]
modifiers   = [{stat="split_count", layer="add", value=2, tags=["rock"]}]
on          = "split"
if          = "source.tags has fire"
do          = "spawn shard ×2 with tags [projectile, fire, shard]"
visual      = {layer="emitter", material="ember", tint="#f0a04b"}
