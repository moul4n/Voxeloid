Research

What the reference games actually do

Every game below solves the same problem: many modifiers, one number, and the requirement that adding a modifier changes the result in a way the player can feel without the result running away. The solutions cluster into a handful of shapes.

Path of Exile

Three layers: flat adds sum, "increased" sums into one bucket, "more" multiplies separately. Every skill carries tags and picks up every matching modifier, so one item line works for hundreds of skills. Damage conversion is one-way (phys → lightning → cold → fire → chaos) and converted damage is scaled by both pools. Conversion happens once; that's the recursion guard.

hit = (base + Σadd) × (1 + Σinc) × Π(1 + more)

Balatro

Two visible numbers, chips × mult. Jokers resolve strictly left to right, so order is a build decision. Retriggers re-run a card, turning additive stacks into exponents; the famous Baron + Mime + Blueprint setup overflows a double. Readable because each joker changes one number by one operation.

score = chips × mult · order matters

Risk of Rain 2

Four explicit stacking curves per item: linear, hyperbolic for anything bounded (chance, reduction), exponential for the deliberately scary ones (Shaped Glass), and special. Hyperbolic exists so 100% is never reached; the cost is that hyperbolic items become dead picks past ~10 stacks.

hyperbolic: a·n / (1 + a·n)

Noita

Modifiers are functions on a shared "shot state" struct, not on spells. Any modifier applies to any projectile. Triggers open a nested mini-wand with fresh state, giving isolation. Divide-by spells carry an iteration counter and collapse past depth 3, which is the recursion guard.

modifier(state) → state · depth cap

Nova Drift

Mods hang off shared categories (projectile, construct, burn, velocity) and each weapon defines what a category-level effect means for it: Splinter Shot fragments Volley, cluster-bombs grenades, only-on-survive for Railgun. One mod, one hook per receiver, no pair code.

mod × receiver-hook, not mod × mod

Vampire Survivors / Brotato

Global stat buckets that stack additively with hard caps (Might +900%, cooldown −90% floor, Amount +10). Weapons reinterpret a global stat per tag (Amount → pierce for Mace, duration for Globus). Brotato's two-layer flat × % formula is PoE's added/increased in miniature.

dmg = (base + Σflat × scaling) × (1 + Σ%)

The Gnorp Apologue

The multiplier is a mostly additive pool driven by gnorp count (the dev tried per-purchase and per-shards-spent first and both misbehaved). A few flat 1.5–5× layers (acid, ice, ultra boost) sit on top, and bomber damage is quadratic in count. No exponential cost wall; growth is bounded by collection throughput. Rust on Tetra, not an off-the-shelf engine.

additive pool × few flat × quadratic counts

Cookie Clicker / Antimatter Dimensions

Cost = base × 1.15ⁿ; income grows polynomially, so exponential cost always wins and prestige resets the curve. AD converts each prestige layer logarithmically (10^(log₁₀x / 308)), so a run 10³⁰⁸× better yields 10× more currency. Softcaps everywhere.

cost_n = b · rⁿ, r ≈ 1.07–1.15

Genshin reactions

Element × element is a small matrix with three response classes (amplify ×1.5/×2, transformative flat damage that can't crit, additive). Three formula shapes cover ~15 pairings. A reaction table is how two tags blend into a third thing rather than one overwriting the other.

tag pair → response class

The pattern. Bucket modifiers by operator, not by source. Same-bucket stacks dilute themselves; cross-bucket stacks multiply. Builds come from crossing buckets, and so does degeneracy. Then make modifiers functions over a tagged state struct so interactions cost O(tags), not O(pairs), and guard recursion with one-way chains and depth counters.

Model

The blending model: five layers and a reaction table

Our stat resolver from the Bible gets two additions from the research: a bounded layer for anything with a ceiling, and a reaction table so tag pairs produce a third behaviour instead of the later one winning.

LayerCombines asUse forFeel
addΣ flatBase damage, projectile count, split countBig early, fades as % layers grow
inc1 + Σ %The common "+40% damage" stuff; most of the poolDiminishing within its own bucket, so one stat can't run away
moreΠ (1 + %)Rare, conditional, tag-gated: "30% more if fire"Where builds actually multiply; ration it
boundedbase + (cap − base) · a·n/(1 + a·n)Crit chance, pierce chance, dodge, cooldown reduction, anything that must never reach 100%Every stack is worth less; never a wall, never infinite
convertMove a fraction of type A into type B; converted part scaled by both poolsLetting one base number be eligible for two tag familiesThe bridge between archetypes; the thing that makes hybrid builds exist

Resolution order

per damage type t in {phys, fire, ice, ...}:
  base_t     = base + Σ add[generic ∪ t]
  conv       = one-way chain, applied once, fractions clamp to 100%
  value_t    = base_t × (1 + Σ inc[generic] + Σ inc[t]) × Π more[generic] × Π more[t]
  converted  = moved × (1 + Σ inc[generic] + Σ inc[from] + Σ inc[to]) × Π more[generic, from, to]
hit          = Σ value_t + converted
hit         *= (1 + crit × (critmult − 1))           # bounded stat, resolved hyperbolically
events       = on_hit / on_kill / on_split → spawn(tags ∪ child_tags), depth += 1, budget −= n

Every tag-gated modifier tests req ⊆ entity.tags, and a spawned child inherits the parent's tags plus whatever the trigger adds. That inheritance is how a "fire projectiles pierce" buff reaches shards spawned by a crit that came from a fire bolt, without anyone writing the fire→crit→shard case.

The reaction table

Where two tags meet on the same entity, a small table says what the pair means. Three response classes cover everything, and adding a tag means adding one row, not N pair rules.

PairClassResult
fire + shardamplifyShards keep burning: child inherits fire, ember trail layer added
fire + icetransformNeither overwrites: entity gains steam, loses both, steam = area + slow, flat damage from level (can't crit)
crit + chainamplifyChain depth budget +1 on crit; the visual layer stacks a second glow
heavy + fasttransformMomentum: knockback = mass × velocity (see physics); becomes ram
shard + shard (child of child)additiveSplit count is inherited at 50%; that's the geometric series that keeps recursion finite
any + wildadditiveWild tag copies one random tag from the parent; makes builds drift

Never overwrite. A buff that says "projectiles are now fire" is the overwrite anti-pattern: it deletes the phys build the player made. The convert layer replaces it: "50% of physical becomes fire" keeps the old modifiers working and makes the new ones work too. If a tag genuinely must replace another, route it through a transform row so the player gets a third thing, not a loss.

Physics

Blending stats into physics without special cases

Because it's 2D and the swarm is shader-driven, "physics" for us is a small set of quantities per entity. The trick is to derive every physical behaviour from resolved stats rather than giving buffs direct control of the body, so buffs that touch different stats blend through the equations for free.

Derived quantityFormulaWhat blends through it
Masssize³ × density_tagBig Shot × Heavy × any tag that changes density
Knockback on hitmass × speed × knock_multSpeed buffs and size buffs both become knockback; a slow heavy shot and a fast light one feel different for free
Bouncerestitution = bounded(bounce_stacks), energy_kept = restitution × (1 − mass_penalty)Bounce count is bounded, so "infinite bounces" is impossible without a special rule
Gravityg × (1 − float) × mass_scaleFloat-tag buffs and mass buffs fight each other naturally
Drag / lifetimelife = base × (1 + inc_life), drag = 1/massHeavy things coast, light things stop; lifetime buffs extend both
Split impulsechildren get parent velocity × 0.7 + radial × split_forceSpeed buffs make shard bursts wider; split count and speed compound visually
Area on deathradius = size × area_inc, dmg = mass × explode_fracBig + explosive + heavy = big slow bombs; nobody codes "big bomb"

The rule: a buff may add a modifier to size, speed, density, bounce, float, life, split_force, explode_frac. It may not set a body property directly. The derived table above is code that never changes; the pool of buffs changes weekly. Every physical quantity that has a ceiling (restitution, pierce, float) uses the bounded layer so the physics never goes non-finite, and because the swarm integrates in the vertex shader, these are all uniforms or per-instance custom data, not RigidBody2D calls.

One idea from Gnorp worth stealing outright: make the global multiplier additive and driven by something visible and slow (there it's gnorp count; here it could be live object count on screen, which also rewards density), then let a handful of tag-gated more layers sit on top. Additive-slow at the bottom, multiplicative-rare at the top is what keeps a run predictable in shape while letting one pick spike it.

Pacing

A stable progress track that doesn't stifle ideas

"Stable" means: the median player's time-to-kill stays roughly flat across the run, the unlucky player still makes progress, and the player who finds a combo pulls visibly ahead. The way to get all three is to separate what the curve controls from what the picks control.

  • The enemy HP curve is tuned to the p50 build under a random-ish picker, never to the best build. The sim gives that number directly.
  • Every offer contains at least one safe generic (an inc or flat buff that works in any build). That's the floor; it stops the p10 run stalling. Slay the Spire's rule: one half of any synergy pair must be fine on its own.
  • Tag-gated buffs are only offered once the tag exists, or they carry a small generic half. Otherwise they read as dead picks; the sim's dead-pick scan is exactly this failure.
  • Offers are weighted toward tags already in the build (loyalty factor ~2–3×) with one wildcard slot ~15% of the time. Snowballing is the point; the wildcard is how runs drift somewhere new.
  • Spikes are allowed but bounded by structure, not by nerfs: depth cap, spawn budget, bounded stats, converted-once. The ceiling comes from the rules, so a new buff can be as wild as we like and still can't go non-finite.
  • Temporary multipliers for the biggest numbers. Cookie Clicker's Frenzy ×7 and Gnorp's +8 for three minutes both let the player taste absurd power without it being the new baseline.
Testing

Mathing out every route: buildsim.py

A pure-Python simulator that implements the model above for a sample pool of 27 buffs and then explores the build space. It runs in about 15 seconds and is the tool we re-run every time the pool changes. The point isn't the sample pool (which is throwaway) but the questions it answers.

PassWhat it doesQuestion it answers
soloEach buff alone vs. baseIs anything worthless or dominant on its own?
synergyEvery pair: (both) / (a × b)Which pairs blend (> 1), which fight (< 1)? Is every family getting a > 1.3 pair?
exhaustiveAll k-subsets of the pool (k = 4: 17,550 builds; k = 6: 296,010)Distribution of power; the true best build and the true worst; p90/p10 and max/p50 spread
dead-pick scanMarginal gain of each buff over 300 random contextsWhich buffs are +0% in most contexts (prerequisite problem)?
Monte CarloThousands of runs with offer-of-3 and three picker policies (random, tag-loyal, greedy)What the real distribution looks like under the offer system, and the skill gap
progress trackPer-pick p10/p50/p90 power vs the HP curve → time-to-killIs the curve tuned right? Does the unlucky player fall behind?
dominancePick rate × lift on final power under greedyIs a buff auto-pick? Is one never picked?

"Every permutation" is only tractable because the resolver is order-independent by construction (buckets, not Balatro's left-to-right), so permutations collapse to combinations. At 27 buffs and 12 picks that's 17.4 million combinations, which is still cheap to sample exhaustively overnight if we ever need to, and the Monte Carlo covers the offer system on top. When the pool reaches 60+ buffs, exhaustive at k = 4 stays instant and Monte Carlo remains the tool for full runs.

Cost of keeping it honest: the evaluator is closed-form (expected damage per second), not a frame simulation. That's what makes millions of evaluations possible, and it's accurate for everything except emergent spatial stuff (a ricochet that happens to bounce into a crowd). Those we test in the game; everything numeric we test here first.

What this buys us. Every new buff idea gets dropped into the pool and the sim tells us within a minute whether it's dead, dominant, or a real combo piece, and what it does to the p10/p50/p90 track, before anyone opens Godot. The pool can be as crazy as we like because the guard rails are structural.

Ideas

A generator for mechanics we haven't thought of

Because every mechanic in the model is trigger × condition × effect × target × layer, the space of possible buffs is a grammar, and a grammar can be sampled. Most outputs are junk; about one in five is a real idea, and one in twenty is something we'd never have written on purpose. Press the button until one of those shows up, then drop it into the sim.

Press Generate.

    The grammar behind it, which is also the spec for the buff resource format:

    WHEN   := on hit | on kill | on split | on crit | on bounce | every N-th shot | when 50+ objects on screen
         | on pickup | when a child dies | on overkill | while standing still | on first hit of each enemy
IF     := (none) | source has TAG | target has TAG | chain depth ≥ 2 | 3+ TAG objects alive
         | hit was a crit | source is a child | target at low HP
DO     := spawn N children [+TAG] at F% damage | convert F% TYPE→TYPE | add MOD(stat, layer, value) to TAG
         | grant TAG to source | retrigger once (capped) | refund cooldown | pull / push nearby
         | leave a zone that applies TAG | duplicate the source | swap two of the source's stats
TARGET := source | its children | all TAG on screen | nearest 3 | the player's next shot
LAYER  := add | inc | more | bounded | convert
TAX    := (none) | −F% rate | −F% damage | consumes a child | shorter lifetime

    Three composition rules make generated ideas usable rather than random: every more or count effect comes with a TAX; every gated effect names a tag that exists in the pool; and any effect that spawns or retriggers goes through the depth and budget guards automatically, so nothing the generator produces can be non-finite.

    Summary

    Rules to build against

    1. Five layers, bucketed by operator: add, inc, more, bounded, convert. Same bucket dilutes, cross bucket multiplies.
    2. Anything with a ceiling is bounded (hyperbolic). Nothing reaches 100%.
    3. Tags on entities, gates on modifiers, inheritance on spawn. No pair code, ever.
    4. Tag pairs resolve through a reaction table with three classes: amplify, transform, additive. Overwrite is not a class.
    5. Conversion is one-way and happens once. Converted damage is scaled by both pools.
    6. Depth cap 6, spawn budget per hit, retrigger cap 3. These are frame-budget guards as well as balance guards.
    7. Physics is derived from stats through fixed equations. Buffs touch stats, never bodies.
    8. Count and retrigger are multipliers in disguise; they carry a tax.
    9. Every offer has one safe generic; gated buffs are offered only once their tag exists; offers are tag-loyal with a wildcard.
    10. The HP curve is tuned to the p50 run under a tag-loyal picker. Target p90/p10 of 3–5×, max/p50 of 5–10×.
    11. Every pool change is run through buildsim before it's run in Godot.
